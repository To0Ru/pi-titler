## 1. 项目概述与定位

`pi-titler` 是面向 **Pi Coding Agent** 体系的自动化会话命名扩展插件（Pi Package）。

### 1.1 核心痛点
* Pi 默认不会自动为新会话生成语义化标题，而是直接截取第一条用户消息作为展示名，极易造成会话列表（`/resume`）可读性差、视觉杂乱。
* 现有部分社区方案代码陈旧未适配新 API、不支持独立轻量小模型、或仅对特定的 Slash 命令生效。

### 1.2 核心目标
* **配置后自动工作**：“自动命名”开关默认开启。用户通过 `/titler` 或配置文件明确指定标题模型后，按工具调用、轮次结束和用户消息数量触发后台异步命名；可关闭自动命名并保留手动重新生成。未指定模型时保留 Pi 默认名称，不自动挑选或探测便宜模型。
* **独立模型分流**：支持使用独立的轻量/低成本标题模型；是否允许失败后改用会话模型由用户配置，默认关闭。会话模型指当前对话所用的模型。
* **保留宿主默认行为**：无法生成标题时不写入替代标题，让 Pi 继续使用默认展示名；对已命名会话进行手动重新生成失败时，保留原名。
* **双语排版友好（CJK-aware）**：按终端实际显示宽度限制标题，默认上限为 40 个宽度单位，约 20 个汉字；语言跟随用户消息的主要语言，技术名词保留原文。
* **零侵入与状态保护**：自动命名不覆盖已有标题，生成过程静默容错。用户主动选择重新生成标题时，可以直接替换已有标题。

### 1.3 自动命名触发规则（已确定）

以下入口共用同一套命名逻辑；前提是已明确配置标题模型，且当前会话允许自动命名、尚无显式标题。

* “自动命名”开关为 `autoNaming`，默认 `true`，支持全局及整套会话独立配置。关闭后跳过全部自动入口，手动重新生成不受此开关限制；生成结果写入前再次检查开关，防止关闭后应用迟到标题。

| 触发时机 | 行为 |
| :--- | :--- |
| 累计完成第三次工具调用 | 读取截至工具返回时的会话上下文，提前后台命名，无需等待整轮结束。 |
| 一轮问答结束（`agent_settled`） | 尚未命名则尝试生成，覆盖零工具调用及只调用一两次的纯问答或轻量任务。只有问候、尚无明确话题时，可在同一次命名请求中返回空结果，留待后续触发。 |
| 累计收到第三条用户消息 | 尚未命名则基于现有对话生成概括性标题，不再仅因话题不明确或偏闲聊而暂缓。模型不可用或调用失败仍按静默失败规则处理。 |

* 工具调用次数跨轮累计；以执行结束为计数时点，成功和失败都计数，同批并行工具分别计数。
* “三句话”指三条用户对话消息，不按句号分句，不把助手回复和工具结果计入用户消息数量。
* 三个入口均检查已有标题与生成锁，避免并发重复请求；写入前再次检查会话身份及标题状态。
* 自动命名成功后保持稳定，不随讨论发展自动改名；用户可通过 `/titler` 主动重新生成。

### 1.4 标题取材与表达（已确定）

* **以当前会话中这个 Agent 的具体任务为中心**，而不是概括整个项目。用户会在同一项目内让多个 Agent 共用 `AGENTS.md` 开发，标题需要区分各个会话的任务。
* 用户表达的任务目标是主要依据，助手回复和工具调用及结果可补充具体对象和发现；共享 `AGENTS.md`、项目介绍等只作为背景。
* 避免将查看目录、读取说明、检查 Git 状态等准备动作误当成最终任务，也避免多个会话都被命名成“开发 pi-titler”。
* 默认最大显示宽度为 40；跟随用户消息的主要语言，代码标识符和技术名词保留原文。

### 1.5 标题模型与失败处理（已确定）

* 首次使用且未明确指定标题模型时，保留 Pi 默认名称，不进行自动模型选择。用户可通过 `/titler` 或直接编辑配置文件指定模型。
* 生成优先使用用户指定的标题模型，遵守宿主模型注册表与鉴权契约。
* 会话模型回退为用户可配置开关，**默认关闭**。两列表格中左栏为“失败时改用”，右栏开启时显示“会话模型”，关闭时显示“关闭”；固定说明区解释“标题模型失败或不可用时，改用当前对话所用的模型”。开启后，指定标题模型失败或不可用时，可以尝试会话模型。
* 不允许回退或回退仍失败时，不设置新标题、不自行截断并写入用户消息；让 Pi 保持原有名称或默认展示名。
* 自动生成与失败处理保持静默，不因失败临时弹窗询问是否调用会话模型。

### 1.6 `/titler` 菜单与手动重新生成（已确定）

* 在 Pi 中注册 `/titler` 扩展命令。首页只保留“重新生成当前会话标题”和“设置”；标题模型统一在“设置 → 标题模型”选择，避免两个入口进入同一页面。
* 打开菜单本身不会改名。用户选择“重新生成标题”即代表授权直接替换当前会话已有标题，**无需二次确认**，包括通过 `/name` 手动设置的标题。
* 手动重新生成应结合当前会话任务与对话进展，不局限于最早的任务；失败保留原名。
* 设置界面使用 **Tab 切换“本会话 / 全局”**，明确显示正在修改的范围，以及本会话处于“继承全局”还是“独立配置”状态。
* 首页、设置和模型选择采用一致的 Pi 列表风格：上下边框、标题、内边距、选中箭头及主题配色。Esc 逐级返回（模型 → 提供商 → 设置 → 首页），首页 Esc 才关闭菜单；返回和切换范围不修改配置。
* 设置页采用两列：左侧简短设置名称，右侧当前值，按终端显示宽度对齐（兼容 CJK）。说明区固定预留两行，选中任何一项都显示对应解释，不因说明出现或换行而改变边框高度。长模型名在一行内省略，不换行撑高；全局页补齐缺少的操作行空间。

### 1.7 全局配置与会话独立配置（已确定）

* 配置既可通过 `/titler` 修改，也可通过配置文件修改。全局菜单修改与直接编辑全局配置文件使用同一份配置来源。
* 会话在未手动修改配置前，实时继承全局设置；全局发生变化，会话的有效配置随之变化。
* **第一次实际保存任意会话配置修改时，复制当时完整的有效配置并应用修改，保存为本会话的整套独立配置。** 从此所有配置项均停止跟随全局，包括用户没有修改的项。
* 仅打开设置、切换 Tab 或取消编辑，不产生会话独立配置。不得擅自改成按配置项分别继承的方案。
* 会话独立配置随会话持久保存，退出 Pi 并再次恢复会话后仍生效。
* 提供“恢复全局配置”操作：清除整套会话独立配置，重新实时使用全局设置。操作行仅显示该名称，右栏留空，不附加“执行”或“已继承”。
* 修改配置影响后续命名，不主动改写已经生成的标题。
* 当前确定的作用范围是全局与本会话；项目级配置曾讨论，但尚未纳入已确定的产品范围。

### 1.8 历史会话（已确定）

* 对已有历史记录但尚未命名的会话，自动补生成标题由用户配置，**默认关闭**。
* 关闭时，恢复旧会话以及恢复后继续聊天，都不会自动为该旧会话补命名；用户启用该功能或手动选择重新生成后，才允许命名。
* 首版实现选择：开启后等待下一次对话事件再检查，或手动重新生成；打开旧会话本身不发起命名请求。通过持久标记区分历史会话与插件启用时的新会话，详见第 5 节。

### 模块职责界定
| 模块 | 职责与禁区 |
| :--- | :--- |
| `extensions/index.ts` | 负责 Pi 生命周期集成、三个命名触发入口、`/titler` 命令及设置界面接入。**禁止在此直接堆砌模型调用和字符处理逻辑**。 |
| `extensions/config.ts` | 统一处理全局配置、会话完整配置快照、恢复继承、持久化和鉴权检查。提供 `resolveTitleModel(ctx)`，遵守显式模型选择与可选回退规则，不自动探测便宜模型。 |
| `extensions/context.ts` | 当前分支证据提取、取材预算、用户/工具计数与提示词。排除系统消息与思考块，优先保留用户目标，不直接调用模型。 |
| `extensions/engine.ts` | 状态锁控制、当前会话任务证据提取、自动与手动命名保护、通过 `ctx.modelRegistry` 进行旁路请求。**必须做好 try-catch 兜底，杜绝抛出未捕获异常**。 |
| `extensions/ui.ts` | 终端菜单与键盘交互，调用配置模块保存设置、调用引擎手动重命名；手动操作可反馈结果，自动命名仍保持静默。 |
| `extensions/sanitize.ts` | 纯函数工具集。负责文字净化（去引号、书名号、废话前缀、标点）及 CJK 终端宽度计算。 |

## 3. Pi Package 核心契约与开发规范

在 Pi 生态中编写扩展必须遵守以下规范，任何 Agent 在编写代码时**不得违背**：

### 3.1 依赖声明规范（至关重要）
* 宿主提供的包：`@earendil-works/pi-coding-agent`、`@earendil-works/pi-ai`、`@earendil-works/pi-agent-core`、`@earendil-works/pi-tui` 等，**必须且只能放在 `peerDependencies` 与 `devDependencies` 中**，**严禁**放入 `dependencies`。
* *原因*：若打包了物理副本，在 ESM 运行时会导致类实例与注册表重复初始化，触发 Pi 核心运行时警告或崩溃。

### 3.2 模型调用契约
* 调用模型必须使用 `ctx.modelRegistry.complete(...)` 或 `ctx.modelRegistry.streamSimple(...)`，不要直接调用第三方 SDK（如直接引入 openai/anthropic npm 包）。
* 检查模型是否可用必须调用 `ctx.modelRegistry.hasConfiguredAuth(model)`，确保已由用户或环境变量配置过有效密钥。
* **按 Pi 1.5.0 实际接口**，跨提供商调用 `streamSimple` 时显式指定 `reasoning: "low"`、`cacheRetention: "none"`。原文的 `reasoningEffort` 是部分提供商专属字段，不属于 `ModelsSimpleStreamOptions`，已在核对类型后修正；禁止为了满足旧字段描述绕过类型检查。

### 3.3 会话与状态保护契约
* **自动命名**：`pi.getSessionName()` 返回非空时，该会话已经显式命名，必须跳过；无论标题来自用户还是系统，都不得自动覆盖。
* **手动重新生成**：用户在 `/titler` 菜单中明确选择重新生成时，可以直接替换已有标题，包括用户手动标题；该例外不得扩展到自动命名入口。
* 必须在内存中维护 `isGenerating` 状态锁，防止三个触发入口和手动请求造成并发冲突。
* 请求发起时记录目标会话及原有标题；返回时再次校验，防止将结果写入切换后的会话，或覆盖生成期间用户另行修改的标题。失败或结果失效时保留原状态。

## 4. 编码与代码风格约定

1. **类型完备**：所有模块必须具备清晰的 TypeScript 类型定义，开启 `strict: true`，严禁随意使用 `any`（若第三方库字段不可控，需采用类型守卫或安全解构）。
2. **纯粹静默与错误隔离**：标题生成属于“次要增强任务”，模型网络超时、429 限流、无有效密钥等情况必须在 `engine` 内部吸收并以空结果返回，**绝不允许中断或打断用户的核心编程会话**。
3. **平台兼容性**：路径处理采用标准化方式，终端字符处理兼顾 Windows / Linux / macOS。
4. **持续维护长期记忆**：讨论、探索、实现、排查和用户反馈都需要及时回写 `AGENTS.md`。记录内容应足以让另一个 Agent 在没有聊天历史的情况下理解背景、约束、进度及下一步，不能只保留最终决定。明确区分用户要求、Agent 建议、推测、待验证事项和已完成工作；调整规则时同步修订相关旧条款，避免同文档内相互矛盾。

## 5. 长期协作记忆

### 5.1 用户场景与协作偏好（2026-11-10）

* 用户会在同一项目内使用多个 Agent，并共享项目 `AGENTS.md`；会话标题需要识别每个 Agent 的独立任务，而非统一概括项目。
* 用户希望既能直接编辑配置文件，也能在 Pi 内通过 `/titler` 完成模型选择和配置修改。
* 产品讨论需要收集选择时，用户明确要求直接使用 question 工具发题；允许用户自由补充，不应只接受预设选项。
* **异步选择题尚未答完时，不要发送结束轮次的 final。** 用户反馈结束后界面上的选择题会消失。应保持轮次打开，等待答复；分题提交时记录已答内容，继续等待其余题目。
* 用户希望 `AGENTS.md` 承担长期记忆与规范双重作用，明确纠正了“只记决定”的做法：讨论内容、背景、过程、偏好、问题和进度也要及时记录，不应等用户提醒才补写。
* 用户随后明确提出“可以开始写代码了吗？”，当前已进入实现阶段；应直接推进实现与验证，不再停留于能力确认。产品规则已确定不等于功能已实现，需持续准确记录进度。
* 讨论潜在产品问题时，不应把 Agent 提出的解决建议直接宣布为要采用的规则。用户曾因 Agent 擅自说要改成“优先主线、明确转向才换主题”而要求停下；该方案尚未经用户确定。应先共同讨论取舍，明确方案后再改代码；讨论记录需标明建议与待定，不伪装成已定规范。

### 5.2 讨论过程与被替代方案（2026-11-10）

1. **命名时机的起点**：原方案仅在首轮结束后命名，但打招呼或“看看项目”等消息可能缺乏任务信息。用户提出以第三次工具调用作为已经开始工作的信号。进一步约定在工具返回后触发，以包含结果上下文；失败调用也有任务信息，计入次数。
2. **纯问答覆盖**：只依靠工具次数会漏掉零工具调用的讨论。Agent 曾建议初版接受不命名，用户要求增加条件覆盖，因此保留每轮结束的兜底入口，并覆盖只调用一两次工具的情况。
3. **闲聊暂缓的上限**：在同一次标题请求中允许对无明确话题返回空结果；用户进一步提出，累计三条用户消息后仍无标题也应命名。由此形成第 1.3 节的三个触发入口，而不是额外增加一次问候分类请求。
4. **标题取材的纠正**：最初讨论“任务目标还是本轮结论”，用户强调核心是当前 Agent 的会话任务。第三次工具调用只是一种触发信号，不保证工具内容足以表达目标，仍须优先结合用户请求。
5. **模型与费用边界**：原架构包含便宜模型探测、自动回退当前模型和截断兜底。用户选择由配置控制是否回退当前模型，默认关闭，失败保留 Pi 默认行为；并明确首次未指定模型时不自动选模型。原自动探测和插件自行截断写标题的方案已被替代。
6. **重新生成的授权**：用户希望在 Pi 内注册 `/titler`。确定命令先打开菜单，选择重新生成后直接替换标题；展示候选再确认的建议未被采用。自动命名仍保护全部已有标题。

### 5.3 实现选择与待验证事项

以下为开始编码后根据 Pi 1.5.0 接口作出的工程选择，不代表重新向用户逐项提问定案：

* **配置文件**：全局文件为 `getAgentDir()/titler.json`，默认 `~/.pi/agent/titler.json`，遵循 Pi 自带的 `PI_CODING_AGENT_DIR`。字段为 `version: 1`、`autoNaming`（默认 `true`）、`model: { provider, id } | null`、`fallbackToCurrentModel`、`nameHistoricalSessions`、`maxWidth`（8–120）。旧全局文件及旧会话快照缺少 `autoNaming` 时按默认开启读取，无需更改版本号。当前不提供逐字段环境变量覆盖，避免菜单展示与有效值不一致。
* **文件保存**：每次重新读取以接收外部修改；保存时排他加锁、合并当前值并原子替换。损坏 JSON 或未知版本拒绝覆盖。自动命名吸收错误，手动菜单提示；异常退出留下锁时显示锁路径供排查，不盲目删除其他进程的锁。
* **会话存储**：通过 `pi.appendEntry` 保存 `pi-titler:config` 自定义条目，`mode: snapshot` 保存完整配置，`mode: inherit` 恢复全局。读取会话全部条目的最新设置，同一会话内 `/tree` 导航不回滚配置；条目不进入主模型上下文。派生会话沿用 Pi 复制过来的条目，尚无额外跨分支覆盖策略。
* **历史识别**：首次观察无标记会话时，有用户消息视为历史会话，否则为新会话；保存 `pi-titler:origin` 标记，重载时复用。开启历史补命名后等下次对话事件；手动重新生成不受历史开关限制。
* **调用策略**：15 秒/模型，`maxRetries: 0`，仅开启对应开关时改用会话模型；失败冷却 30 秒，等后续自然事件重试，没有定时重试。手动调用可立即重试。同一证据请求去重；生成期间的新事件合并成一次待处理请求，避免遗漏第三条用户消息。
* **取材预算**：当前分支的用户消息、助手可见文本/工具调用描述、有限工具结果。用户单条最多 2,500 字符、助手 1,500、工具 1,000；总量目标约 12,000 字符、最多 24 条。自动命名保留初始与最近用户目标；手动命名保留最近三条用户目标及近期证据。系统提示词、思考块、插件元数据不作为取材。
* **运行模式**：自动命名事件可用于非交互模式；菜单要求 `ctx.mode === "tui"`，其他模式提示可以直接编辑配置文件。
* **实测范围**：用户已提供真实终端菜单截图并参与多轮验收，另报告一次 200 多 k 上下文会话手动命名准确且调用输入约 3k。自动化测试仍只使用模拟模型；多任务样本下的标题质量、各提供商延迟和后续 Pi 版本兼容性尚待验证。配置升级迁移和派生会话特殊行为，随实际需要继续补充。
